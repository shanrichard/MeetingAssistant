# macOS 会议助手方案

状态：原型持续迭代；自动化检查与真实会议验收范围见 [验证与验收](验证记录.md)。

## 已确认的产品行为

- 全系统声音和真实麦克风分别采集，统一时间轴；系统声音排除本助手输出。
- Google Meet（Chrome）、Zoom、Teams 共用系统音频采集层。
- 会中原文字幕与译文；仅区分音频来源“我 / 系统声音”。
- 结束后保存实时原文与录音，直接基于实时原文生成文字总结及证据引用。不进行会后录音重转写、翻译或说话人识别。
- 发言翻译通过虚拟麦克风送入会议，对方不需要安装软件；一场会议使用一个对外目标语言。
- 每个用户填写自己的 OpenAI API Key，点击“保存”后安全保存至本机 macOS Keychain，下次启动可继续使用。无共享 Key、无开发者代理后端。
- 不使用发布功能开关。开始、暂停、结束、发送译音是明确的用户操作。唯一自动发起的模型请求是会前说明：已连接 Google 并保存 OpenAI Key 时，会议开始前 24 小时内自动生成，使用用户自己的额度。

## 技术实现

SwiftUI/AppKit 原生桌面应用，Swift Package Manager，无第三方包依赖，macOS 14.2+。

系统声音使用 Core Audio Process Tap：global mono mixdown，排除本进程，unmuted，私有 aggregate device。麦克风使用 AVCaptureSession + AVCaptureAudioDataOutput，以设备 UID 明确选择物理输入设备，由系统管理蓝牙音频格式变化。两轨按实际缓冲区格式转换为 24 kHz、mono、PCM16；麦克风采样时间通过 capture session 的 synchronizationClock 映射到主机单调时钟，与系统声音对齐。开始时先确认麦克风已送出缓冲区，设备中断或捕获失败须明确提示，不能继续显示正常录制。

0.1.5 每轨独立连接 Realtime translation WebSocket，翻译模型为 `gpt-realtime-translate`，输入转写配置为 `gpt-live-transcribe`，接收原文与译文的流式增量。连续发送包含静音的 24 kHz PCM，不等待本地分句、转写完成或文字翻译队列。每个连接独立发送，积压有上限并明确提示；结束发送 `session.close` 并有界等待尾段，未确认的尾段明确提示，保留已收到的原文和本地录音。

同一会话的原文与译文使用 `elapsed_ms` 音频帧时钟归入发言段，源文本在两路内容之后出现至少两秒间隔时开始下一段；迟到增量仍更新对应旧段。它是连续语音段的对照，不是严格的逐句对齐。采集时间映射保留暂停与重连间隙。暂停结束当前会话，恢复建立新会话，避免跨暂停拼接。

录音按五分钟 WAV 分块，单块约 14.4 MB，便于本地保存和崩溃恢复。文件和 meeting.json 保存于 `~/Library/Application Support/MeetingAssistant/Meetings/<UUID>/`，不包含 Key。持久化记录原文、译文、时间、状态和故障信息；旧版 speaker ID 与其他历史字段保持读取兼容。退出或崩溃后保留已有原文，修复本地 WAV 文件头，再由用户对已有原文生成总结。暂停期间的音轨保留时间间隙。

实时字幕采用单列，上方突出对方译文，下方弱化原文，自己的发言和说话人信息降低视觉权重，不显示段落编号。新段和已有段落增长均自动跟随；用户上翻时暂停，点击“回到最新”恢复。会中另有半透明悬浮字幕：非激活浮动面板置于会议窗口（含全屏）上方，背景透明度可调，最新字幕在底部、旧字幕淡出，可拖动、调整大小和开启鼠标穿透，录制结束后自动隐藏。会议总结使用 `gpt-5.6-luna`，长会议分段总结、最终汇总和引用校验重试统一使用该模型。总结请求用连续整数作为原文序号，结构化输出限定当前批次的序号范围；本地验证后精确还原为持久化 segment ID，不让模型抄写长编号。每份分段总结先校验再汇总；不存在的证据引用不得进入正式结果。

0.1.9 移除文件转写和说话人识别链路，不保留入口或隐藏开关。实时原文是唯一总结来源；即使实时原文缺失、空白或总结失败，也不会转而上传录音。只显示音频来源，不推断系统声音内的个人身份；总结不得把音频来源当成待办责任人。

已有实时原文、历史转写、说话人映射与录音独立保留。全文始终默认显示实时原文，旧版历史转写可切换查看。历史总结的引用按原始 ID 跳到对应记录，并说明与当前总结来源的差异；导出保留历史引用的锚点。缺失的实时字幕不会自动补全。

结束流程先停止采集、排空实时音频队列并有界等待最后字幕，保存全部收到的原文、录音索引与时长，保存成功后才发送文字总结。自动总结和“生成总结 / 更新总结”统一调用 `gpt-5.6-luna`；不改变录音、已有原译文、说话人映射及历史处理进度。成功后状态为 complete，失败保留已保存的原文及旧总结，允许重试。无有效实时原文时在读取凭据或发请求前返回明确提示。

同一次结构化总结响应返回内容标题，使用总结语言，中文优先 8–24 字、最长 80 字符；长会议以最终汇总标题为准。标题与总结一起保存，默认时间名称及自动生成的名称可更新，手动名称始终保留。记录名称来源以避免覆盖用户改名；旧记录缺少来源时，仅匹配当前格式下的默认时间名称才自动替换。请求返回后基于最新记录应用结果，保留请求期间的手动改名；无效标题、请求失败或保存失败不更新内存中的名称与总结。

## 向会议发送翻译语音

真实麦克风 → 独立 `gpt-live-1` 会话（固定用户所选音色、默认 `marin`、仅翻译提示词）→ 流式 PCM → 指定虚拟输出设备 → 会议软件的虚拟麦克风。实时字幕继续使用各自的 `gpt-realtime-translate` 会话。

0.1.5 移除实时发送中的转写、文字翻译、TTS 串行等待。现对外发送使用 GPT-Live 的连续音频会话，建会话时固定模型和用户所选音色（设置提供 13 个已确认的选项），自动重连也沿用该声音。发送译音期间禁用音色选择，需先停止发送再更换；选择自动保存，旧版偏好升级默认 Marin 并保留语言和设备设置。不保证目标语言原声透传。只在用户点击发送后建立对外翻译会话，不回放之前发言，不承诺原声复刻。真实会议中的音色一致性、翻译质量和延迟需单独验收。

首次打开应用检测已有 BlackHole 2ch 并自动保存输出选择，保留用户已有的可用虚拟输出设置。缺少时提示从官方服务器下载并安装；下载和安装必须由用户点击触发，校验固定 SHA-256、发布者签名及 Gatekeeper 后交给系统安装器完成管理员授权。安装文件已存在但 HAL 设备未就绪时提示重启，不重复安装。设备实际出现后自动配置；首次跳过后可在设置继续。安装包不随应用再分发，界面保留 BlackHole 与 Existential Audio 的归属说明。

只向指定虚拟设备写入译音。0.1.10 起，开启同传时接管并回读系统默认输入，用户主动停止、暂停、结束及正常退出时恢复，异常退出后下次启动恢复；系统输出不改变，会议软件需跟随系统默认输入。首次设备配置只保存应用偏好，不改变系统路由。物理麦克风选择排除虚拟设备；译音输出只允许同时具有输入和输出的虚拟设备。停止译音、暂停、结束时取消未完成生成并清空播放队列；译音故障时停止播放并保持虚拟麦克风静音，界面显示恢复原麦克风操作，不擅自切换到原音。会议软件自身静音独立于助手，界面必须说明。

## 凭据和数据

- 设置页 SecureField 接受用户输入，只提供“保存”。Keychain 支持保存后读回校验、更新、删除；保存失败保留输入，不将未保存的 Key 用于 API 请求。UserDefaults 只存语言、设备和非敏感的配置状态；旧版术语字段保持兼容，不再提供无效设置入口。
- 当前运行缓存已验证可读的 Key，避免每次 API 调用都重复访问钥匙串。授权失败引导完成系统授权或回设置重新填写并保存，不把系统授权错误误报为 OpenAI Key 错误。
- Key 只发送至固定 `https://api.openai.com` / `wss://api.openai.com`；禁用凭据请求重定向；不写入日志、会议文件或导出。
- 用户点击开始后才采集；开始会议会将音频发送至 OpenAI，消耗自己的 API 额度。
- 无 Key 时仍可查看历史、设置语言、枚举设备；不调用真实模型。
- Google 授权（refresh token 与账号）保存在单独的 Keychain 项，只发送至固定的 `oauth2.googleapis.com`、`www.googleapis.com` 与 `gmail.googleapis.com`，同样禁用重定向，不写入偏好、会议文件、日志或导出。UserDefaults 只记已连接的邮箱和已授权范围用于显示。
- 会前说明会把日历邀请、相关邮件和历史总结发送给 OpenAI（组织管理员已确认可行）。缓存在 `~/Library/Application Support/MeetingAssistant/Briefs/`（目录 0700、文件 0600），会议结束 7 天后清理，断开 Google 账号时全部删除；会议记录保留开始时附上的那一份。导出的 Markdown 只带被引用的邮件主题，不含邮件正文。
- 录音仅作为本地记录保留，用户可从 Finder 管理文件。会后总结只发送文字。分享 Markdown 不包含录音和凭据。

## 日历与邮件上下文

目标是通过 Google Calendar、相关 Gmail 邮件和历史会议，为同一场会议提供会前说明、会中背景和会后变化总结。

状态：已实现——连接 Google 账号、读取主日历、未来会议列表与日程详情、临近会议入口、所有开始入口统一关联、补关联与更正、Gmail 检索、自动生成会前说明、会后总结对照会前背景。

### Google 接入方式（组织统一配置）

核心用户是同一 Google Workspace 组织的同事。组织的 GCP 管理员配置一次，全公司零配置使用；项目不提供共享客户端，也不需要开发者后端。

- GCP 项目建在组织下，启用 Google Calendar API 与 Gmail API（第二期使用）。OAuth 同意屏幕选 Internal：只有组织账号能授权，不需要 Google 审核、CASA 安全评估，没有 100 用户上限和测试状态的 7 天 token 过期。组织外账号会被 Google 以 `org_internal` 拒绝。
- 客户端类型为“桌面应用”。Client ID 与 Secret 保存在不入库的 `Config/google-oauth-client.json`（也接受从 Google Cloud 下载的 JSON），`build-app.sh` 在签名前写入应用 Info.plist；缺少该文件时构建出的版本不显示日历功能。桌面客户端的 Secret 按 Google 说明并非机密，但 Internal 客户端泄露会被用于针对同事的钓鱼授权，因此不提交到公开仓库，只随公司构建分发。其他组织或个人用自己的客户端文件构建即可。
- 授权使用系统浏览器 + 回环地址回调（`127.0.0.1` 随机端口）+ PKCE + state 校验，不使用内嵌 WebView。请求 `openid email`、`calendar.events.readonly` 与 `gmail.readonly`，只读。早先只授权了日历的连接，在侧栏、日程详情和设置中提示“授权读取邮件”，重新授权即可；Google 拒绝邮件请求时本地标记为未授权并继续只用日历。每次连接都请求同意以确保拿到 refresh token；重新连接后撤销旧 token，断开时撤销并删除 Keychain 项，已关联的记录保持不变。
- 若 Workspace 管理后台限制了第三方应用访问 Calendar 或 Gmail，需要超级管理员在“安全性 → API 控制”中信任内部应用。
- 设置中的“Google 账号”页统一管理连接，下设“日历”“邮件”“会前说明”三部分，说明读取范围、自动生成时机和发送给 OpenAI 的内容。连接不必进入设置：侧栏“即将开始”区和欢迎页都可一键连接，授权失效时同一位置提示重新连接。
- 同步诊断写入 `~/Library/Application Support/MeetingAssistant/calendar-sync.json`，只含状态、错误、时间和数量，不含日程标题、人员或账号。
- 同步按需轮询：读取尚未结束、7 天内开始的日程实例（`singleEvents=true` 展开重复会议），每 5 分钟一次，失败 1 分钟后重试；应用回到前台按间隔补同步，唤醒、系统时间或时区变化立即同步。没有后端，不使用推送。授权失效（`invalid_grant`）后停止自动同步并提示重新连接。
- 第一期只支持一个公司账号，候选日程不做跨账号去重；关联仍保存账号，便于以后扩展。

### 未来会议与日程详情

侧栏在会议记录之上显示“即将开始”：列出尚未结束的会议（排除全天、已拒绝、已取消、专注时间与外出），最多 6 场。日程以卡片显示，与会议记录明确区分：左侧色条、浅色底，时间在前、下方为“今天 / 明天 / 周几”，临近的改为倒计时并加深颜色，已有记录的显示勾选标记。分区标题右侧的“全部”在详情区按天分组展示 7 天内的全部会议。搜索同时过滤日程标题。日程和会议记录共用侧栏选中状态，选中记录会替换日程。

点开日程在详情区显示：标题、日期时间、倒计时、是否重复会议、“开始《会议名称》”（已有记录时为“追加记录”）、“加入会议”、受邀人与回复状态（注明不代表出席）、本场记录，以及同一重复系列的历史记录。在详情页明确点击开始，即使离开始还早也可以开始并关联；顶部提醒卡片不重复显示正在查看的这场。

### 临近会议成为主要开始入口

已确认要求：日历会议临近开始时，界面必须强化显示，并明确提示用户直接开始这场会议，避免用户从普通入口创建未关联日程的会议。

首版采用开始前 10 分钟进入强调状态（`CalendarSchedule.lead`）；这个时长是待体验验证的设计值，不设置发布功能开关或隐藏功能参数。到达开始时间后改为“已到开始时间”；日历时段尚未结束且用户尚未开始记录时，继续显示，覆盖用户迟到或稍晚打开应用的情况。

- 在主窗口详情区顶部展示会议卡片，即使用户正在浏览历史记录也能看到；侧栏主按钮同步改为“开始《会议名称》”，多场时改为“选择要开始的会议…”。卡片显示标题、起止时间、距开始时间、受邀人摘要；会前说明属于第二期。
- 日历读取失败时，在同一位置显示“日历未同步，临近会议可能未显示”及重试或重新连接，不把读取失败显示成没有会议。
- 提醒目前只在主窗口内显示；应用在后台或窗口关闭时不会弹出系统通知。
- 主操作明确写为“开始《会议名称》”，含义是开始记录并关联这条日程。打开 Meet、Zoom 等会议链接使用独立的“加入会议”操作，避免把打开会议链接误认为已开始记录。
- “开始临时会议”保留为次要入口（侧栏链接、选择界面按钮、菜单 ⇧⌘N）。没有临近或进行中的候选日程时，正常提供普通开始入口。
- 提醒本身不会启动录音。已有会议正在记录或暂停时，当前会议控制保持优先；下一场日程可以提示，但不会抢占或替换正在进行的记录。

### 所有开始入口使用相同的关联流程

侧栏、欢迎页与应用菜单中的 ⌘N 统一调用 `MeetingController.requestStart()`：先确定要开始的日程或临时会议，再进入录制流程，避免快捷键绕过日程关联。只有明确的“开始《会议名称》”“开始临时会议”才直接开始。

1. 用户点击明确标有会议名称的日历主操作，一次点击即可创建已关联的记录。
2. 用户从通用按钮、菜单或 ⌘N 开始时，如果有尚未记录的候选日程，先展示轻量选择界面，列出窗口内全部日程，并保留“开始临时会议”。不能只凭时间静默选择。已有记录的日程在选择界面标注“已有记录”，提供“查看记录”和“追加记录”。
3. 多场会议时间重叠时，展示标题、时间、组织者和所属账号供选择，不自动绑定第一条。全天事项、已取消或用户已拒绝的日程不作为默认开始推荐。
4. 应用恢复前台、电脑唤醒、系统时间变化和日历同步更新时重新计算推荐状态，界面倒计时每 20 秒刷新。日程改期后更新提醒；已有记录的日程实例不再占据开始主入口，日程结束后也不再出现。

### 在开始时保存关联并允许纠正

创建记录时就在 meeting.json 的 `calendar` 字段保存 Google 账号、日历标识、事件实例 ID、`recurringEventId`、`originalStartTime`、iCalUID，以及标题、计划时间、组织者、受邀人及应邀状态和会议链接。重复会议以实例 ID 区分每一次发生（改期后不变），不凭标题关联。实际录制时间（`createdAt`）与计划时间分别保留。旧记录缺少该字段时视为未关联。

关联记录默认使用日程标题，记为自动名称并以 `calendarNamed` 标记来自日程：总结生成的标题不会替换它；补关联会替换自动名称，手动名称始终保留；取消关联时回到总结标题或默认时间名称。标记单独存放、不新增名称来源取值，旧版应用仍能打开已关联记录（旧版更新总结时会按自动名称处理）。

记录及其日程关联保存成功后才开始采集。关联保存失败时明确报错，不降级成一场用户不知情的普通会议。邮件检索和会前说明生成可以继续进行，不阻塞已确定日程的开始操作；离线或同步失败时明确显示来源状态，不把“没有取到日程”解释成“没有会议”。

同一时间只能有一场记录；记录进行中，开始入口全部停用，卡片只提示下一场日程。已有记录的日程实例不再出现在卡片中；选择界面和记录详情（日程未结束时）提供明确的“追加记录”。

如果用户已误开临时会议，记录详情提供“关联日历会议…”，列出记录开始前后 12 小时内的日程；已关联记录可“更改关联…”或“取消关联”。补关联保留录音、原文、实际开始时间和手动名称，已有总结保持不变，不悄悄改写旧总结；保存失败时界面不显示为已关联。补关联目前只在记录结束后可用，录制中暂不提供。

### 背景贯穿会前与会后

**会前说明**自动生成：有其他受邀人、未结束、24 小时内开始的会议，按开始时间依次生成，一次一场。日程标题、时间、受邀人或说明变化后重新生成；开始前 1 小时内若已生成超过 6 小时，补一次最新邮件；新授权邮件后，未含邮件的说明重新生成；失败后 30 分钟内不自动重试，详情页可手动“重新整理”或“重试”。

- 来源：日历邀请（含 HTML 转成的说明文字）；相关邮件——近 60 天与其他受邀人往来的线程，以及近 90 天提到会议标题的线程（标题过于通用如“周会”“Weekly sync”不搜；受邀人超过 15 人只搜标题），排除日历通知、推广和社交邮件，两类都命中的排前，最多 8 个线程、每个取最近 3 封，去掉引用的旧邮件，每封最多 1200 字；同一重复会议最近 3 次有总结的记录。
- 输出：会议目的、相关往来、上次结论、待确认事项四部分，每条必须引用来源编号，本地校验后换成稳定的来源 ID，引用无效则重试一次后报错；只保留被引用的来源。提示词声明所有来源都是不可信数据，邮件里的指令一律忽略；提议保持为提议，不写成决定；与会议无关的邮件不提及。
- 展示：日程详情的“会前说明”区，每条下方是来源标签，点开可看邮件主题、发件人、时间、摘录并在 Gmail 中打开，历史会议可直接打开记录；临近会议卡片提供“会前说明”入口；录制中可从实时字幕顶部打开。开始关联会议时把当时的说明附到记录上，记录详情多一个“会前说明”页。
- 诊断：`brief-diagnostics.json` 只记数量、时间和错误信息。

**会后总结**：记录带有会前说明时，作为编号背景随原文一起发送，在原有四部分之外再给出“相对会前的变化”（必须同时引用本次原文和背景）和“会前事项未讨论”（引用背景，原文可为空）。关联了日程但没有说明的记录，总结前先按记录保存的日程信息补生成一份（邮件只取会议结束次日之前的），失败则只基于原文并在状态中说明。没有说明时请求与以前完全相同。背景引用会换成说明里的邮件、日历或历史会议来源显示。

受邀人和应邀状态用于会议背景，不当作实际出席或发言身份的证明。本次会议决定、邮件中的提议和历史会议结论分别保留来源及时间；本次决定和承诺仍需有本次实时原文支持。

### 入口验收场景

已有离线检查覆盖：重叠会议都列出、通用入口不静默选择、账号断开后拒绝开始而不降级成临时会议、补关联保留数据、更正与取消关联、保存失败不改界面、迟到仍可开始、结束后退出入口。仍需在真实环境验证：临近开始时主界面强化显示；迟到或唤醒后仍能找到当前日程；侧栏、欢迎页、菜单和 ⌘N 均走关联流程；重叠会议要求选择；改期、取消和重复会议实例处理正确；重复点击不创建重复记录；下一场提醒不打断当前录制；关联保存失败不创建无关联记录；邮件检索失败不阻塞已关联会议开始；误开后可补关联且原有数据完整保留。

## 验收与证据边界

自动化验证：乱序与重复转写事件；本地停顿分句；音频时钟映射；WAV 头和分块；断点持久化；实时原文保护、空输入拒绝与历史引用兼容；Responses 不完整返回；请求的授权和固定域名；字幕/总结证据引用。译音取消和队列隔离已实现，仍需真实设备验收。

人工验证：首次权限、真实 API、Meet/Zoom/Teams 三类会议、USB/蓝牙设备、耳机/外放、设备切换、至少两小时会议、中英混说、网络中断、暂停/恢复/结束、虚拟麦克风输出和静音。

没有真实用户 Key 时只执行离线测试，不把接口实现当作在线验证。没有实体会议测试时不宣称三平台兼容验证通过。首版建议耳机：双轨采集本身不等于外放回声消除。面向他人正式分发前需要 Developer ID 签名、公证及驱动安装体验验证。
